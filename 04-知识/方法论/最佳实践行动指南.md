# 最佳实践行动指南：从每天到五年的个人运行协议

> 本文回答两个问题：每个时间尺度最应该做什么；具体怎么执行、记录和验证。
>
> 本文的主要信源限定为 `03-资源/素材库/`。`SOURCE_OF_TRUTH.md` 仅用于确认本库当前路径、版本和事实状态，不作为生活建议的外部证据。

## 一、证据与参数规则

### 1. 证据标签

| 标签 | 含义 | 可以怎么写 | 不可以怎么写 |
|---|---|---|---|
| `[S]` | 素材中可定位的原始研究、原书或原始资料 | “素材引用某研究提出……” | “科学已经证明所有人都……” |
| `[A]` | 素材作者基于多个来源形成的判断 | “素材作者据此主张……” | “这是公认事实” |
| `[B]` | 从素材编译出的个人行动建议 | “建议作为个人实验运行” | “所有人必须这样做” |
| `[P]` | 个人实验参数 | “当前版本设为90分钟，复核日期……” | “90分钟是普遍最优值” |
| `[待验证]` | 缺少本人记录、真实用户数据或完整原始来源 | “待记录后判断” | “已经有效” |

### 2. 权威度边界

1. 素材中的人物故事只能说明“存在这种路径”，不能证明成功概率。
2. 素材中的精确数字、收入、粉丝、用户和产品数据，使用前必须重新核验时间、口径和原始出处。
3. 素材中的健康、心理、营养、运动和睡眠内容不能替代医生或其他专业人员的个体化建议。
4. 财务动作只讨论记录、风险边界、现金流和验证流程，不提供具体证券买卖指令。
5. 计划、目标、模拟数据和候选阈值不得写成已经完成的事实。
6. 一个动作只有留下文件、数据、链接、版本或可观察结果，才算完成。

### 3. 初始候选参数表

下表不是普遍标准，只为首次运行提供起点。每项均为 `[P]`，必须根据个人数据复核。

| 参数 | 初始候选值 `[P]` | 来源位置 | 适用边界 | 首次复核 |
|---|---|---|---|---|
| 能量基线 | 连续5个工作日、每小时一次 | `人生操作系统-v3-04-时间能量.md`“协议A” | 只用于发现个人时段 | 基线结束次日 |
| 连续工作块 | 45分钟+10分钟离屏+45分钟 | 同上“协议B” | 根据产出和疲劳调整 | 运行2周后 |
| 低门槛身体活动 | 不超过15分钟 | `人生操作系统-v3-02-健康.md`“系统设计任务” | 健康限制优先 | 运行2周后 |
| 紧密关系名单 | 不超过15人 | `人生操作系统-v3-10-关系.md` | 不是关系质量标准 | 每月 |
| 无动作草稿归档 | 30天 | `KNOWLEDGE_MAP.md`防熵规则 | 本库治理规则 | 每周 |
| 深审数据窗口 | 最近3个月 | 本指南自定初值 `[P]` | 用于形成趋势；数据不足明确留空 | 每月 |
| 最小作品周期 | 24小时内 | `人生操作系统-v3-06-创造.md`系统任务 | 只用于压缩范围 | 每次执行后 |

### 4. 数字类型规则

正文中的数字分四类：

1. **个人参数 `[P]`**：时间长度、频率、名单规模、回顾窗口；可调整，必须在正文就地标 `[P]`，或纳入候选参数表/参数变更表。
2. **流程结构**：例如五字段行动卡、四类月度台账、三种财务情景；用于组织信息，不宣称这是自然规律。
3. **记录量表**：例如睡眠质量1–5、能量1–10；只是压缩主观记录的序数工具，不代表医学刻度。只要求同一人、同一量表持续使用。
4. **示例数量**：例如“三个要点、一个反例”；用于演示最低输出格式，不是效果阈值。执行时可调整，但必须保留“主动回忆、边界或反例、行动”三个功能。

章节标题中的 `0–15分钟`、`15–45分钟`、`第1–5小时`、`入睡前60分钟` 属于初版日程占位参数 `[P]`。个人基线完成后必须改成自己的相对时段；文档维护时同步更新参数表。

### 5. 参数变更格式

所有时间、频率、阈值和目标数字都按个人参数管理：

```text
参数名：
旧值：
新值：
数据区间：
调整证据：
调整原因：
生效日期：
复核日期：
```

首次运行时不追求所谓最优值。先按素材提供的最小协议运行，再用个人记录校准。

## 二、每天：相对时间运行模板

### 每天最重要的事

`[B]` 本指南建议把每天的个人实验收敛到以下五项；这是素材编译出的优先顺序，不是普遍事实：

1. 睡眠和身体没有被工作持续透支。
2. 个人最高能量窗口用于唯一核心产出。
3. 输入必须转化为判断、动作或作品。
4. 重要关系发生一次真实连接。
5. 睡前留下第二天可以直接启动的第一步。

固定时钟不是通用最佳实践。初版按候选参数表运行能量基线 `[P]`；基线结束后，按单位时间可见产出和主观疲劳调整深度工作时段。

### 0. 每日输入

每天开始前需要四项输入：

| 输入 | 来源 | 缺失时怎么处理 |
|---|---|---|
| 昨日睡眠记录 | 每日记录 | 当天补记实际入睡、起床、醒来次数和主观质量 |
| 本周唯一核心问题 | 周计划 | 没有则先写出本周要解决的一个问题 |
| 当前项目的下一交付物 | `01-项目/` 或 `05-内容生产/进行中/` | 没有交付物则不能进入深度块 |
| 前一天留下的第一步 | 海明威之桥记录 | 没有则用5分钟写出可立即执行的动作 |

### 起床后0–15分钟 `[P]`：记录身体基线

**输入**：纸质笔记本或每日记录工具。

**步骤**：

1. 记录实际入睡时间、起床时间、夜间醒来次数。
2. 给睡眠质量打1–5分；只记录主观状态，不做医学诊断。
3. 记录起床后第一小时能量分数1–10。
4. 接触自然光、饮水等动作按个人环境执行；这些是素材中的候选协议 `[B]`，不是治疗建议。
5. 起床后15分钟内不打开社交媒体或消息流。

**产出**：一条完整睡眠与晨间能量记录。

**记录位置**：个人每日记录；若尚无固定工具，使用一个连续表格，不为每天新建文件。

**完成判定**：四个字段均有值；没有“睡得还行”等不可比较表述。

### 起床后15–45分钟 `[P]`：身体激活与当天任务确认

**输入**：本周核心问题、当前项目文件、个人运动限制。

**步骤**：

1. 按初始候选参数表进行低门槛身体活动 `[P]`。动作选择必须符合个人健康状态；素材中的俯卧撑、深蹲、步行只是示例 `[B]`。
2. 打开当前项目文件，只确认一个当天核心交付物。
3. 把交付物改写为“动词+对象+可验收状态”。
4. 写出启动句：“当我进入第一个高能量窗口时，我打开___，完成___的第一步___。”

**合格示例**：

- “完成 `RESEARCH_LOG.md` 中3个核心主张的来源定位。”
- “把第2章改到每个主张都有来源、边界和反例。”
- “让产品的导入功能通过现有测试并留下测试结果。”

**不合格示例**：

- “推进项目。”
- “努力写作。”
- “学习AI。”

**产出**：一个当天核心交付物和一个启动句。

**记录位置**：当前项目状态页或每日记录。

**完成判定**：第三方能够仅凭句子判断当天是否完成。

### 起床后第1–5小时 `[P]`：个人最高能量窗口

> `[A]` 素材把深度注意力视为稀缺资源，并建议保护连续时间块。具体出现时间因个人而异。

**输入**：核心交付物、相关文件、已关闭的非必要通知。

**步骤**：

1. 开始前关闭消息、邮件、社交媒体和无关浏览器标签页。
2. 只打开完成核心交付物所需的文件。
3. 运行一个连续工作块。初版按候选参数表执行 `[P]`；复核时用可见产出、打断次数和疲劳记录调整。
4. 工作块中不得切换到第二个项目。
5. 结束时写三行：完成了什么；还缺什么；下次第一步是什么。
6. 若连续5个工作日记录显示另一时段产出更高，将工作块迁移到个人高峰，不固守早晨。

**产出**：一个可见增量，例如：

- 新增或修订的文件；
- 已定位的来源条目；
- 通过的测试；
- 完成的访谈记录；
- 可供审阅的内容版本。

**记录位置**：项目文件、Git提交、草稿版本或研究日志。

**完成判定**：留下文件差异、提交、记录或可复现测试，不以“专注了多久”替代产出。

### 起床后第5–7小时 `[P]`：进食、步行与低负荷恢复

**输入**：个人饮食限制、健康状态和当天步行条件。

**步骤**：

1. 进食时不处理工作消息。
2. 饮食按个人情况执行。素材提出“优先未加工食物、每餐安排蛋白质、减少含糖饮料”等候选原则 `[A/B]`；不把它们写成个体医疗结论。
3. 安排一次步行或其他低负荷活动；时长作为个人参数记录。
4. 如果输入内容，必须在结束后不看资料写出三个要点、一个反例、一个24小时内动作。

**产出**：恢复记录；如有输入，留下“四项学习记录”。

**记录位置**：每日记录或对应学习笔记。

**完成判定**：输入内容至少转化为一个判断或动作；只看完不算学习完成。

### 起床后第7–11小时 `[P]`：第二工作窗口

**输入**：上午剩余工作、协作事项、KBLoop当前阶段。

**步骤**：

1. 先检查上午核心交付物是否完成。
2. 未完成：继续同一交付物，不另开项目。
3. 已完成：按以下顺序选择下一任务：研究与证据定位；结构化；写作或制作；终审；协作。
4. 邮件和消息集中处理，不在工作块中穿插。
5. 结束时写下第二天第一步，并标注具体文件路径和动作。

**产出**：核心交付物完成，或一个已定义边界的下一版本。

**记录位置**：当前项目目录或内容生产目录。

**完成判定**：当前项目状态明确为 `完成 / 待核实 / 阻塞` 之一，并写明阻塞原因。

### 起床后第11–14小时 `[P]`：关系、创造与学习

`[B]` 每天只选择其中一个主题，不同时做三类任务；这是降低任务切换的编译建议。

#### 关系日

- **输入**：按候选参数表维护的紧密关系名单 `[P]`；人数不是关系质量门槛。
- **步骤**：选择本月尚无实质互动的一人；发送具体问题、近况或对方真正需要的信息；如有冲突，记录待修复事项。
- **产出**：一次有内容的双向交流，或一个已发送的联系动作。
- **记录**：对象、日期、主题、后续动作；不记录隐私细节。
- **判定**：不是群发、点赞或表情互动。

#### 创造日

- **输入**：按候选参数表压缩到短周期可完成的作品单元 `[P]`。
- **步骤**：定义受众、问题、最小成品；完成可展示版本；记录未解决问题。
- **产出**：文章片段、代码功能、图稿、录音、模板或产品页面之一。
- **记录**：项目目录和版本说明。
- **判定**：别人可以查看、测试或评价。

#### 学习日

- **输入**：一个当前项目真实需要的问题。
- **步骤**：先不看资料写已有理解；定向查资料；合上资料重述；写一个反例；在项目中实际使用。
- **产出**：问题答案、来源、反例和应用结果。
- **记录**：`04-知识/原子笔记/` 或项目研究日志。
- **判定**：有实际应用；“读完”或“看完课程”不算完成。

### 计划入睡前60分钟 `[P]`：卸载与次日启动

**输入**：当天未完成事项、次日固定责任、每日记录。

**步骤**：

1. 停止处理新的工作输入。
2. 把脑中仍在循环的事项写下，不要求文采。
3. 给当天压力或焦虑感打1–5分，仅作为趋势记录。
4. 为第二天写一个核心交付物和第一步。
5. 记录计划入睡时间和实际熄灯时间。

**产出**：压力卸载记录、次日交付物、次日第一步。

**记录位置**：每日记录和当前项目状态页。

**完成判定**：第二天开始工作时不需要重新决定“从哪里开始”。

## 三、每周：七天交付链

### 每周最重要的事

`[B]` 每周只推动一个真实问题完成一次完整闭环；这是降低在制品数量的编译建议：

`真实问题 → 来源检索 → 形成判断 → 制作可验证版本 → 终审或测试 → 发布/交付 → 记录反馈`

一周完成多个互不相关的半成品，不如完成一个可核验闭环。

### 周一：选择问题与定义验收

**输入**：`05-内容生产/选题管理/00-选题记录.md`、项目状态页、上周反馈。

**步骤**：

1. 从候选问题中选一个有真实来源的问题。
2. 写明问题来自哪里：本人记录、用户访谈、评论、数据或项目阻塞。
3. 写出本周交付物、受众、用途和验收条件。
4. 列出已知证据和缺口。
5. 将任务加入当前项目或发布队列；进行中总数遵守现有WIP规则。

**产出**：一条本周任务卡。

**记录位置**：选题记录或项目状态文件。

**完成判定**：任务卡含 `问题来源 / 交付物 / 截止日 / 验收条件 / 阻塞项`。

### 周二：研究与主张审计

**输入**：周一任务卡、`03-资源/素材库/`、当前知识卡。

**步骤**：

1. 先检索素材库，再检索知识层，禁止跳过库内检索直接生成正文。
2. 将核心主张拆为独立条目。
3. 每条主张记录：来源路径、原文位置、证据类型、边界、反例、状态。
4. 无法定位来源的精确数字删除、降级为待验证，或改写为不含数字的有限主张。
5. 区分“来源作者认为”“本指南建议”“本人数据表明”。

**产出**：`RESEARCH_LOG.md` 或等价研究台账。

**记录位置**：`05-内容生产/进行中/[任务]/` 或项目目录。

**完成判定**：至少一个核心主张可精确返回来源；待验证项有明确列表。

### 周三：结构与最小可验证版本

**输入**：研究台账。

**步骤**：

1. 用 QST/CON/OPI/CAS/SOL 检查问题、概念、观点、案例和方案是否齐全。
2. 写一句核心判断和适用边界。
3. 为每个主要段落分配一条主张和一条证据。
4. 写一个反例或失败条件。
5. 产出最小可审阅版本，不追求一次完成体系。

**产出**：结构稿和最小版本。

**记录位置**：当前任务目录。

**完成判定**：审阅者可指出“同意/不同意哪条主张”，而不是只看到素材堆积。

### 周四：成稿、制作或功能完成

**输入**：结构稿和研究台账。

**步骤**：

1. 完成正文、功能、设计或交付物。
2. 把事实、推断、建议和参数分别标注。
3. 删除虚构经历、不可查案例、无来源数字和模板残留。
4. 扫描禁用词、重复表达和AI脚手架。
5. 每个行动建议写清输入、步骤、产出、记录和判定。

**产出**：可终审版本。

**记录位置**：当前任务目录，版本命名使用日期或语义版本。

**完成判定**：不存在“以后补来源”“此处加案例”等未处理占位符。

### 周五：终审、测试和发布准入

**输入**：可终审版本、研究台账、发布准入规则。

**步骤**：

1. 逐条核验核心主张。
2. 检查适用边界、反例、风险和停止条件。
3. 对内容执行事实、表达和平台适配检查；对产品执行测试和验收。
4. 只有实际发布后，才能更新发布数据和已发布归档。
5. 没有通过门禁时，记录具体阻塞，不伪造发布事实。

**产出**：`FINAL`版本、验证报告，或带阻塞原因的返工任务。

**记录位置**：发布后写入 `05-内容生产/运营与发布/数据/数据统计表.csv` 和 `已发布/`；未发布仍留在进行中目录。

**完成判定**：发布链接或可复现测试结果存在；否则状态不得写“完成”。

### 周六：旗舰作品或产品实验

**输入**：`SOURCE_OF_TRUTH.md` 中当前旗舰路径、个人基线或当前项目。

**步骤**：

1. 选择一个可在当天形成外部可观察增量的任务。

3. 完成后记录文件数、字数、测试、数据条数或反馈。

**产出**：旗舰作品或产品的一个新版本增量。

**记录位置**：对应项目目录；不得修改冻结来源版。

**完成判定**：与当天开始前相比，可以用文件差异或数据变化证明进展。

### 周日：数据复盘与下周结构

**步骤**：

5. 沉淀1–3条有来源、有判断、有边界的知识；数量是候选参数 `[P]`。

## 四、每月：事实台账与一个领域深审

### 每月最重要的事

`[B]` 本指南把月度动作编译为四类事实台账和一个领域审计，以降低多领域同时浅审的负担：

1. 财务与资源事实；
2. 关系与反馈事实；
3. 内容、作品与产品事实；
4. 系统参数与异常事实。

### 第1周：财务与资源事实

**输入**：银行流水、支付账单、收入和费用记录；不凭记忆填写。

**步骤**：

1. 记录期末现金、投资账户、应收、负债和当月净现金流。
2. 区分生存支出、经营支出、资产投入和可选消费。
3. 计算现金跑道：可支配现金 ÷ 月度必要支出。
4. 记录自动扣款、订阅和工具费用。对没有实际使用记录的项目先审查合同期限、退款条件、数据导出、账号依赖和迁移风险，再决定保留、降级或取消。
5. 财务目标和预测单独列，不与实际数字混写。

**产出**：月度财务事实表。

**记录位置**：个人财务台账；本指南不指定证券或具体配置。

**完成判定**：所有数字可回到流水；事实、目标、预测分栏记录。

### 第2周：关系与反馈事实

**输入**：实际互动记录、访谈、评论和冲突事项。

**步骤**：

1. 列出本月发生实质互动的人、日期、主题和后续动作。
2. 把反馈分为赞同、疑问、反例、需求、购买或合作信号。
3. 冲突只记录事件、影响和待修复动作，不给对方做心理诊断。
4. 选择一个需要跟进的人，确定下月具体联系动作。

**产出**：关系与反馈表。

**记录位置**：隐私安全的个人记录；公开内容不得暴露他人未经许可的信息。

**完成判定**：每条反馈对应原话、来源或实际事件；没有“大家都觉得”之类概括。

### 第3周：内容、作品与产品事实

**输入**：Git历史、文件版本、发布链接、平台后台、产品和用户记录。

**步骤**：

1. 分开统计：新建草稿、通过门禁、实际发布、收到有效反馈、完成真实交付。
2. 每个发布稿记录平台、日期、链接和后台数据。
3. 每个产品记录版本、真实使用者、数据条数、问题和下一实验。
4. 统计素材输入和知识输出，检查是否持续收集却没有形成个人判断。
5. 从本月研究中更新QST/CON/OPI/CAS/SOL内容单元；每条保留来源。

**产出**：月度内容与产品事实表。

**记录位置**：内容数据台账、产品记录和项目目录。

**完成判定**：发布、交付和用户数据都有可核验证据；草稿不得计为发布。

### 第4周：领域深审与参数调整

`[B]` 每月只深审一个领域；这是避免十二个领域同时浅审的编译建议。

| 月份 | 领域 | 必查数据 | 必须形成的决策 |
|---|---|---|---|
| 1月 | 健康 | 睡眠、能量、活动和压力记录 | 调整一个健康参数或保持不变并写理由 |
| 2月 | 时间能量 | 各时段能量与实际产出 | 确定个人最高能量窗口 |
| 3月 | 学习 | 输入、提取练习、实际应用 | 停止一个无产出的输入源 |
| 4月 | 财富 | 流水、跑道、收入来源和交付成本 | 选择一个需验证的现金流命题 |
| 5月 | 创造 | 可展示产出、反馈和返工 | 选择一个下一月重点作品 |
| 6月 | 关系 | 实际互动和待修复事项 | 确定一个维护或修复动作 |
| 7月 | 认知 | 决策记录、错误类型和信息源 | 建立一个事前阻断脚本 |
| 8月 | 决策 | 预测、概率、结果和偏差 | 调整一个决策规则 |
| 9月 | AI协作 | Agent任务、完成率、人工返工 | 自动化一个重复任务或停止一个低效Agent |
| 10月 | 意义 | 心流、贡献、关系和自主记录 | 停止一个只服务外部认可的任务 |
| 11月 | 系统整合 | 十二领域趋势和资源冲突 | 处理一个侵蚀其他领域的冲突 |
| 12月 | 元系统 | 默认、脚本、能量、纠错、自更新 | 升级、删除或重建一个MRU |

**深审步骤**：

1. 拉取最近3个月真实数据；没有数据就写“无数据”，不能用印象代替。
2. 将事实、解释和建议分成三栏。
3. 找一个持续异常、一个有效做法和一个待验证假设。
4. 只调整一个参数。
5. 写参数变更记录和下次复核日期。

**产出**：一份月度领域审计表。

**判定**：有数据、有边界、有单一参数变更；没有同时修改多个变量。

## 五、每半年：删减、校准和重新分配

### 半年最重要的事

`[B]` 本指南建议半年复盘形成四类决策：保留、冻结、归档和未来六个月的资源集中方向。

### 输入

- 过去6个月项目状态和文件差异；
- 发布、产品和用户事实台账；
- 财务流水与现金跑道；
- 决策日志和每月领域审计；
- `SOURCE_OF_TRUTH.md` 中当前版本事实。

### 步骤1：项目处置

对 `01-项目/` 每个活跃项目填写：

| 项目 | 目标交付物 | 最近30天证据 | 下一步 | 处置 | 理由 |
|---|---|---|---|---|---|
| | | | | Keep/Freeze/Archive | |

- `Keep`：最近30天有文件、测试、访谈或交付进展，且未来30天有明确下一步。
- `Freeze`：暂不投入，但写明重新启动的外部条件和复核日期。
- `Archive`：目标取消、已完成或长期无动作且无重启条件。

### 步骤2：方向一致性

1. 统计深度工作时间实际投入的前三个方向。
2. 统计过去6个月产出物数量和外部反馈来源。
3. 对比半年前设定的核心命题。
4. 只基于时间和产出判断方向是否一致，不凭感觉。

### 步骤3：信息源与工具

1. 导出或查看过去90天信息源和工具的实际使用记录。
2. 保留能产生项目动作、知识笔记或作品的来源。
3. 停止没有任何转化记录的付费订阅或工具；是否停止需考虑合同和数据迁移。
4. 新增来源必须写明它要支持哪个当前问题。

### 步骤4：内容与产品校准

1. 统计实际发布稿、有效反馈、需求访谈、真实付款、退款和交付成本。
2. 当前位置只能依据事实标记：研究节奏、重复需求、付费验证、可重复交付或资产化。
3. 没有数据时保持 `[待验证]`，不得提前写“已找到产品市场匹配”。
4. 未来6个月只选择一个最关键的验证命题。

### 产出

- 半年项目处置表；
- 一条未来6个月核心命题；
- 一份信息源与工具停止清单；
- 一个内容或产品验证实验。

### 完成判定

核心命题必须写成：

```text
在____日期前，针对____对象，通过____交付物，验证____命题。
证据是____。
若出现____，则停止或调整。
```

## 六、每年：事实复盘、资产盘点与下一年交付物

### 年度最重要的事

`[B]` 本指南建议年度复盘形成三类产出：年度事实、重复模式和少数可验收交付物。

### Day 1：年度事实表

#### 输入

12个月的周记录、月度台账、Git历史、文件版本、发布数据、财务流水、项目处置和关系反馈记录。

#### 步骤

1. 为每个指标画12个月趋势；缺失月份明确留空。
2. 标注项目、健康、关系、财务和环境事件。
3. 不直接把时间上的同时发生写成因果。
4. 对每个转折点写两个解释：支持解释的证据；可能的替代解释。

#### 产出

一份年度事实表和一条事件时间线。

#### 判定

每个趋势可返回原始数据；没有数据的领域不评分。

### Day 2：五类资产盘点

| 资产 | 只记录什么事实 | 不允许什么 |
|---|---|---|
| 财务 | 余额、负债、现金流、跑道、真实收入和成本 | 以目标替代实际数字 |
| 知识 | 有来源的原子笔记、枢纽卡、连接和实际调用记录 | 用文件数量等同知识质量 |
| 内容 | 实际发布、链接、后台数据、持续反馈 | 把草稿计为发布 |
| 关系 | 实际互动、合作、反馈和待修复事项 | 给他人贴心理标签 |
| 能力 | 已完成作品、测试、认证、交付或迁移证据 | 仅以“学过”证明会了 |

#### 产出

五类资产年度对照表：年初值、年末值、证据、变化、边界。

#### 判定

每类资产至少有一个可定位证据；若无则写“未建立记录”。

### Day 3：重复模式与下一年选择

#### 重复错误审计

1. 汇总月度决策日志。
2. 将错误归类为：信息不足、概率高估、情绪干扰、未设退出路径、执行偏差或外部变化。
3. 只选择出现次数最多的一类错误。
4. 为该类错误建立一个事前阻断脚本。

阻断脚本格式：

```text
当我在____情境准备做____类决策时，
必须先查看____数据，
写下____三个结果及概率，
向____复述决策，
满足____条件后才执行。
```

#### 下一年核心命题

核心命题必须能直接推出下一周的动作，并包含对象、交付物和证据。

不合格：“明年做得更好。”

合格：“在下一年12月31日前，为____对象完成____版本，通过____条真实使用记录验证____问题是否被解决。”

#### 下一年三个交付物

每个交付物填写：

| 交付物 | 权威路径 | Q1 | Q2 | Q3 | Q4 | 验收证据 | 失败状态 |
|---|---|---|---|---|---|---|---|
| | | | | | | | |

#### 停止清单

每项必须写：停止的具体行为、过去一年消耗、实际产出、替代动作和释放时间。

### 系统版本升级

对每个MRU只做三种决策：

- `保持`：数据稳定、仍服务当前目标；
- `升级`：明确新增一个能力、协议或记录；
- `删除`：无使用、无数据或不再服务当前目标。

不得仅修改版本号而没有行为和数据变化。

### 旗舰作品年度核验

按 `SOURCE_OF_TRUTH.md` 确认当前路径，再核验：

1. 年初和年末文件数、字数或功能差异；
2. 新增可定位来源数；
3. 新增真实数据或用户记录数；
4. 实际发布、测试或交付状态；
5. 冻结来源版是否保持只读。

最终回答只能是：“增加了什么、验证了什么、仍阻塞什么。”

### 步骤2：倒推资产与能力

### 步骤3：财务情景而非单点预测

计算三种情景：保守、基准、进取。每种情景写：

- 当前可支配现金；
- 月度必要支出；
- 税后经营或工资现金流；
- 可验证的非工时收入；
