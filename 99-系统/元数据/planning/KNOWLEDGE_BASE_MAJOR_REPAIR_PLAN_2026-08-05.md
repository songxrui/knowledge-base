# KnowledgeBase 全库审计与大修计划

> 审计日期：2026-08-05  
> 计划状态：待批准执行  
> 核心判断：当前知识库不是“缺少一次清理”，而是 Git、文件系统、知识证据、项目组合、内容发布和自动化门禁六套治理机制没有形成同一个闭环。继续零散修补会增加迁移差异和版本债，必须按依赖顺序大修。

## 1. 决策摘要

### 1.1 总体结论

当前知识库仍可检索，核心 MOC 的直接链接大体可用，已发布层也没有混入虚假发布记录。但整体处于高风险维护状态：

1. Git 迁移从未形成可信检查点，`7730` 条工作区差异使任何批量暂存、迁移或回滚都不可靠。
2. `01-项目/` 被当作代码运行目录使用，依赖、缓存和构建材料占据绝大多数文件，知识库承担了不属于它的索引和备份成本。
3. `04-知识/` 中大量健康、营养、心理和金融卡片使用精确数字、强因果或绝对措辞，但缺少统一的证据状态和可机器检查的来源结构。
4. 项目、缓冲区、版本命名、根目录和系统元数据持续漂移，说明 7 月修复没有变成日常机制。
5. 内容生产有草稿和候选，但没有真实发布记录与数据回流，知识库的目标闭环仍未运行。
6. 当前质量门禁能运行，但覆盖范围过窄，`P0=0` 不能代表知识库整体健康。

### 1.2 大修优先级

| 等级 | 含义 | 当前数量 | 处理策略 |
|---|---:|---:|---|
| P0 | 继续操作会扩大不可逆差异或传播高风险知识 | 3 组 | 立即冻结相关写入，先建立基线和隔离 |
| P1 | 结构和流程持续退化，已经影响可信度与维护成本 | 8 组 | 在 P0 稳定后按依赖分批修复 |
| P2 | 不立即阻断，但降低可发现性、自动化和长期效率 | 4 组 | 在结构稳定后补齐 |
| 已接受残余风险 | 用户明确跳过或依赖外部真人动作 | 3 组 | 记录责任人和重新启用条件，不宣称已解决 |

### 1.3 不应采取的动作

- 禁止执行无审计的 `git add -A`、全库移动、全库重命名或全库格式化。
- 禁止因同名就删除 `01-%E9%A1%B9%E7%9B%AE/`；其中 3 张图与正常路径同名文件哈希不同。
- 禁止直接删除全部重复文件；精确重复中包含测试证据、平台图标和有意保留的版本快照。
- 禁止直接修改 `08-媒体与产品/媒体/flagship/book-v7/`。
- 禁止用免责声明替代健康、医疗和金融主张的来源核验。
- 禁止把候选稿或“准备发布”状态写入 `已发布/` 和数据表。

## 2. 审计范围与口径

### 2.1 权威顺序

本计划发生冲突时，按以下顺序解释：

1. `SOURCE_OF_TRUTH.md`
2. `KNOWLEDGE_MAP.md`
3. `HOME.md`
4. `99-系统/README.md`
5. 历史审计、计划、脚本清单和自动生成索引

### 2.2 扫描范围

| 项目 | 口径 |
|---|---|
| 结构审计 | 全目录，包括隐藏运行目录、媒体、项目和系统元数据 |
| Git 审计 | `git status --porcelain=v1 -uall` 与最近提交 |
| 内容质量审计 | 活跃 Markdown，重点统计大于等于 500 字节的实质文档；排除归档、供应商依赖、生成目录和缓冲区 |
| 重复审计 | 排除归档和主要生成依赖后的 SHA-256 精确重复；不把语义相似当成重复 |
| 链接审计 | 活跃 Markdown 的 Obsidian wikilink 启发式解析；代码示例中的 `[[...]]` 可能产生少量误报 |
| 缓冲区审计 | 所有名为 `00-缓冲区` 的目录，以 30 天为超期线 |
| 发布闭环 | 进行中草稿、发布队列、已发布目录和数据统计表四处交叉核对 |

### 2.3 本轮没有执行的动作

- 未批量移动、删除、改名或重写文件。
- 未暂存或提交 Git 差异。
- 未调用外部发布、凭据轮换或真人验证。
- 未修改冻结书稿。
- 除质量门禁此前刷新其 `LATEST` 报告外，本轮只新增本计划文档。

## 4. 问题分级与根因

## 4.1 P0：立即停止扩散

### P0-01 Git 迁移悬空

**风险：** 无法区分迁移、删除、复制、重写和新增；批量暂存会把未知损失固化进历史。  
**根因：** 大规模迁移没有拆成可验证提交，迁移清单与实际工作区又继续分叉。  
**停止条件：** 在迁移检查点完成前，禁止全库重命名、目录清理和批量内容改写。

### P0-02 生成依赖侵入知识库运行边界

**风险：** 任何全库扫描都被约 5.1 万个生成文件放大，备份和索引成本持续上升。  
**根因：** 把“项目说明”与“实时软件代码工作区”混为同一个 Vault 目录。  
**停止条件：** 禁止在 Vault 内重新安装依赖或生成大型构建缓存，直到确定代码工作区策略。

### P0-03 高风险成熟知识缺少主张级证据

**风险：** 未核验的健康和金融内容被 `04-知识/` 的成熟层级赋予过高可信度，并可能进入公开内容或付费产品。  
**根因：** 当前门禁只检索段落中的来源词，不检查“每个精确主张是否有对应来源、证据等级和适用边界”。  
**停止条件：** 相关卡片在完成审计前不得作为事实材料直接发布或用于产品承诺。

## 4.2 P1：结构性修复

| ID | 问题 | 根因 | 直接后果 |
|---|---|---|---|
| P1-01 | 项目组合超出 WIP 规则 | 没有项目状态和退出机制 | 资源被 11 个以上项目分散 |
| P1-02 | 缓冲区债务反弹 | 只有一次性清理，没有 owner、created、expires | 321 个超期文件继续污染搜索 |
| P1-03 | 根目录和编码目录污染 | 自动化输出没有路径 allowlist | 业务媒体失去上下文，出现异常路径 |
| P1-04 | 版本与 canonical 债 | 用文件名表达状态，没有版本注册表 | 72 个版本化文档难以判断当前版 |
| P1-05 | SOT、项目 README、系统 INDEX 漂移 | 权威文件没有一致性检查 | 导航和真实结构不一致 |
| P1-06 | 成熟知识元数据覆盖低 | 没有最低 schema 和迁移策略 | 无法自动筛选成熟度、来源和风险 |
| P1-07 | 发布闭环未运行 | 生产量被当成主要完成指标 | 24 个草稿没有真实反馈 |
| P1-08 | 门禁覆盖过窄 | 只检查少量内容表达模式 | 自动报告与真实风险不一致 |

| ID | 问题 | 改进方向 |
|---|---|---|
| P2-01 | MOC 只列文件，不显示状态 | 增加 status、evidence、canonical、risk 视图 |
| P2-02 | 精确重复缺少处置标签 | 区分 intentional、generated、candidate、remove |
| P2-03 | 系统脚本清单停留在 7 月 | 每个 active 脚本记录输入、输出、最近验证日期 |
| P2-04 | `.playwright-mcp/` 等运行目录进入 Vault | 迁移到外部运行区或明确 99-系统下的短期缓存策略 |

## 5. 目标状态

大修完成后，知识库必须同时满足以下状态：

1. Git 可以回答每个删除和新增的来源，工作区在每个修复波次后可回滚。
2. Vault 只保存项目知识、必要源代码或稳定证据，不保存可重建依赖和大型运行缓存。
3. 所有高风险成熟知识都有主张级来源、证据等级、适用边界和状态；未核验内容留在资源或候选层。
4. 每个活跃项目有 owner、目标、结束条件、状态和最后复核日期，活动项目不超过 3 个。
5. 每个正式知识主题只有一个 canonical，其他版本有明确归档映射。
6. 所有缓冲文件有期限和处置结果，超期数量为 0。
7. SOT、HOME、KNOWLEDGE_MAP、项目清单、MOC 和系统 INDEX 相互一致。
8. 内容生产至少完成连续 3 次“真实发布、数据记录、复盘、方法更新”闭环。
9. 自动门禁可以检测 Git 漂移、生成目录、缓冲区超期、根目录污染、canonical 缺失和高风险无来源主张。

## 6. 执行总原则

| 原则 | 要求 |
|---|---|
| 先基线后修改 | 每一批先输出文件清单、数量、哈希或 Git diff 基线 |
| 一批一目的 | Git 迁移、依赖清理、内容修订、导航更新不得混在同一提交 |
| 先隔离后删除 | 对不确定内容先进入对应 `00-缓冲区/` 或 `90-归档/`，附处置清单 |
| 证据优于文件名 | `final`、`终极`、`合并版` 不构成 canonical 证明 |
| 来源对应主张 | 一个段落出现“来源”不能自动覆盖该段所有数字和因果主张 |
| 外部动作需授权 | 发布、推送、凭据轮换等继续遵守显式授权边界 |
| 冻结来源不修改 | `book-v7` 只读，修复只能发生在派生版或勘误表 |
| 修复后立即验收 | 每批必须检查数量、旧路径、断链、差异和回滚材料 |

## 7. 大修执行波次

## Wave 0：写入冻结与可恢复基线

**目标：** 在任何大改前建立可重复的事实快照。  
**依赖：** 无。  
**预计：** 0.5-1 天。

| 任务 | 动作 | 输出 | 验收 |
|---|---|---|---|
| W0-01 | 记录修复期间允许写入的路径和禁止区 | `repair-freeze-policy.md` | 明确 `book-v7`、归档和当前项目边界 |
| W0-02 | 导出 Git 状态、文件数量、目录体积、根文件、缓冲区和版本命名基线 | 时间戳化 CSV/MD | 指标与本报告可复算 |

## Wave 3：高风险知识隔离与主张级审计

**目标：** 防止未核验健康和金融主张继续被成熟层和内容产品复用。  
**依赖：** Wave 1；可与 Wave 2 后半段并行。  
**预计：** 3-7 天。

### 3A. 建立最小知识 schema

每个成熟知识文档至少包含：

```yaml
type: knowledge
status: verified | provisional | blocked | deprecated
canonical: true | false
risk: normal | health | finance | legal | safety
evidence_level: primary | secondary | expert-summary | personal-observation | unverified
sources:
  - id: SRC-001
    locator: URL/书名页码/本地来源路径
    verified_on: YYYY-MM-DD
reviewed_on: YYYY-MM-DD
```

### 3B. 审计顺序

| 批次 | 范围 | 动作 | 验收 |
|---|---|---|---|
| W3-01 | 65 张风险卡 | 建立 claim ledger，逐条提取数字、因果、绝对词和建议 | 每条主张有 ID 和处置 |
| W3-02 | 58 张来源结构不足风险卡 | 补来源、降级措辞、限定边界或标记 blocked | 未核验主张不再处于 verified |
| W3-03 | 健康/医疗 | 优先原始研究、系统综述、权威指南；区分相关、机制推断和因果 | 精确数字可定位到来源位置 |
| W3-04 | 金融/交易 | 区分个人规则、历史观察和普遍建议 | 不使用“唯一正确”等无边界结论 |
| W3-05 | 候选与资源层 | 将无法核验但有保留价值的内容降级 | 不删除原始来源，不冒充成熟知识 |

**回滚：** 原文先做哈希清单；内容修订与状态降级分开提交。  
**停止条件：** 来源只能追到二手转述但正文仍保留精确因果结论，或改写超出来源支持范围。

## Wave 5：缓冲区清债与版本 canonical 化

**目标：** 消除临时区反弹和版本命名失控。  
**依赖：** Wave 1、Wave 4 项目状态。  
**预计：** 3-5 天。

### 5A. 缓冲区处置

| 处置 | 条件 | 目标位置 |
|---|---|---|
| promote | 内容已验证且符合正式层 schema | 对应正式职责目录 |
| archive | 有历史价值但不再活动 | `90-归档/` 对应映射目录 |
| delete-generated | 可重建、无独立证据价值 | 删除并记录生成方式 |
| retain-temporary | 仍有明确任务依赖 | 原缓冲区，补 owner 和 expires |
| blocked-review | 无法判定 | 保留，指定复核人和期限 |

验收：321 个超期文件全部有处置；超期数量为 0；每个缓冲区有 README 或 manifest，新增文件必须记录 `created`、`owner`、`expires`。

### 5B. 版本治理

| 任务 | 动作 | 验收 |
|---|---|---|
| W5-01 | 为 22 个版本密集目录建立 version family | 72 个命名项全部归属某个 family |
| W5-02 | 每个 family 指定一个 canonical | active 层不存在两个 canonical |
| W5-03 | 历史版进入归档并保留替代映射 | 旧链接可追踪到新版本 |
| W5-04 | 禁用 `final`、`终极`、`最终版` 作为状态机制 | 状态由 frontmatter 和注册表表达 |
| W5-05 | 为冻结/发布产物保留不可变版本号 | 版本号只服务外部引用和可重复构建 |

**回滚：** 先生成 family 清单和链接反向索引，再移动版本；每批移动后重跑链接检查。
